## 2026-11-07T14:14:25.863Z — Assistant (final_answer)

That section is meant to answer two questions before we write code: **How will a project use data validation?** and **What will our tests prove?**

The proposed usage is:

1. A project passes a pandas DataFrame and quality rules to `validate_data`. It gets a report—for example, “age has one missing value; zero allowed.”
2. A project uses `run_validated_step` to perform an operation that depends on valid data. That helper checks the data first. If a required check fails, it reports the failure and prevents the operation from running.

Those function names and signatures are proposals for review.

“Public test boundaries” means testing what a project can observe through those functions. For example:

- Does validation report the correct missing-value count?
- Does a required failure prevent the project operation from creating its output?
- Does the same behavior work when the toolkit is installed in a separate project?

The section also identifies what those tests **cannot prove**: they do not establish that training works, that splits are correct, or that arbitrary project code cannot bypass validation.

The reason to include this before implementation is to agree on what “block supported pipeline steps” means in issue #15. The report function is straightforward; the proposed operation wrapper is a design choice that needs your review. The section currently mixes that decision with too many details, which obscures its purpose.

It means **stop an operation that needs valid data when a required data check fails**.

“Supported pipeline steps” means operations invoked through the toolkit’s provided functions. It cannot prevent someone from writing separate Python code that ignores the checks.
