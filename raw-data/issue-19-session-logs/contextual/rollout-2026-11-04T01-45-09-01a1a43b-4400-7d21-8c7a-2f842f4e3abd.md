The [verification document](/workspaces/agentic-ml/docs/verification/us-05-ip1.md) is a **proposed contract for implementation**, not evidence that validation already works. IP1 produced the design; IP2 will implement and test it.

It makes these decisions:

- **Keep structural planning separate.** US-03 checks that inputs are well formed and stay within declared boundaries. US-05 adds checks that algorithms, parameter names, types and combinations are supported.
- **Start with two algorithm metadata profiles:** `dummy_classifier` and `dummy_regressor`. These provide a small classification/regression baseline for exercising validation. They do not introduce training adapters.
- **Validate configurations and individual candidates.** Configuration checks assess the permitted search space. Candidate checks assess one proposed parameter set before future training.
- **Preserve fixed values and defaults.** Omitted parameters receive recorded registry defaults. Candidates cannot change those values unless the experiment inputs explicitly authorize tuning them.
- **Reject incompatible search spaces conservatively.** If a space permits an invalid combination, reject the configuration—even if some combinations would work. For example, allowing the `quantile` strategy while allowing a null quantile fails validation.
- **Preserve validation evidence separately.** Store the plan identity, registry, defaults and version information. Changed inputs or versions require fresh validation.

Two limits matter. First, a configuration may pass metadata validation even when its ML library is absent; that absence is recorded, and a future training adapter must check installation and compatibility. Second, these APIs cannot stop arbitrary Python from bypassing them. Future execution entrypoints must enforce validation before training.

The final sections define the public tests IP2/IP3 must implement. The only checks actually completed in IP1 were document review, link checks and whitespace checks. Approving IP1 would approve these contracts and test boundaries; executable behavior remains unverified.

The proposal has four public Python interfaces. Together, they follow this flow:

**Registry → configuration validation → candidate validation**

| Interface | What you provide | What it returns |
|---|---|---|
| `validate_registry(...)` | Optional additional algorithm metadata | A checked registry with an identity, or diagnostics |
| `validate_configuration(...)` | Project root, US-03 plan ID and optional registry file | A validated configuration, saved evidence and validation ID, or diagnostics |
| `validate_candidate(...)` | Project root, validation ID, algorithm and proposed parameters | Complete effective parameters—including fixed values and defaults—or diagnostics |
| `inspect_validation(...)` | Project root and validation ID | Preserved configuration plus checks that its evidence is intact and current |

For example, `validate_configuration` might accept a search space where `quantile` ranges from `0.1` to `0.9`. A later `validate_candidate` call checks whether one proposed value, such as `0.5`, obeys that configuration. It also fills in omitted defaults and rejects changes to fixed parameters.

`inspect_validation` checks whether previously saved validation can still be used. Changes to the plan, registry, library versions or applicable approvals block reuse.

The CLI exposes the project-facing operations:

```text
agentic-ml config validate ...
agentic-ml config inspect ...
agentic-ml candidate validate ...
```

CLI results are JSON. Exit codes distinguish success (`0`), rejected input (`2`) and operational failure (`1`).

These interfaces are **proposed and awaiting IP1 approval**. A successful result means the parameters passed validation; it does not authorize or start training.

## 2026-11-04T02:32:50.137Z — Assistant (final_answer)

All four interfaces are proposed exports from `agentic_ml.validation`. They validate metadata and parameters; none starts training or grants execution authority.

### 1. `validate_registry`

```python
validate_registry(
    declarations: RegistryDocument | None = None,
) -> RegistryResult
```

Checks the algorithm definitions that configuration and candidate validation will use.

**Input**

With no argument, it validates the packaged built-in profiles: `dummy_classifier` and `dummy_regressor`.

An optional document adds algorithm metadata:

```text
schema_version: "1.0"
algorithms:
  - id
    interface_version
    tasks
    adapter
    library
    parameters
    requires_non_null
```

Each parameter specification declares its accepted scalar types, default and optional choices or numeric bounds. Combination rules can express requirements such as “when strategy is quantile, quantile must be non-null.”

Additional registrations cannot override built-ins. The function treats declarations as data and never imports a component or executes a validator supplied by the user.

**Checks**

It rejects duplicate IDs, unsupported versions, malformed parameter domains, invalid defaults and invalid combination rules. It also enforces document size and complexity limits.

**Result**

| Field | Meaning |
|---|---|
| `status` | `valid` or `blocked` |
| `registry` | Canonical combined registry; `None` on failure |
| `registry_id` | Content-derived `sha256:…` identity; `None` on failure |
| `diagnostics` | Blocking problems |

A valid registry means its metadata is internally consistent. It does not prove that supplied metadata accurately describes executable code.

### 2. `validate_configuration`

```python
validate_configuration(
    request: ConfigurationRequest,
) -> ConfigurationResult
```

Checks an experiment’s complete permitted configuration and saves immutable validation evidence.

**Request**

| Field | Meaning |
|---|---|
| `project_root: Path` | Explicit experiment repository root |
| `plan_id: str` | Existing US-03 plan identity |
| `registry: Path \| None` | Optional additive registry file, resolved against the project root |

The caller supplies a preserved plan ID rather than an arbitrary configuration mapping. That binds validation to the inputs, decisions and boundaries already recorded by US-03.

**Checks**

The function first verifies that the plan is intact, current and `input_ready`, with applicable delegated approvals present. It then checks:

- Registered algorithm IDs and task compatibility.
- Parameter names, types and allowed values.
- Declared and effective search boundaries.
- Fixed parameters and omitted registry defaults.
- Compatibility of every permitted combination.

The combination policy is conservative. For example, a search space permitting the quantile strategy and a null quantile is rejected, even if it also permits valid combinations.

**Successful output**

| Field | Meaning |
|---|---|
| `status` | `valid` |
| `validation_id` | Content-derived identity of the saved configuration |
| `configuration` | Resolved configuration and provenance |
| `diagnostics` | Empty |

The configuration records fixed values, untunable defaults, remaining search domains, plan and registry identities, harness/library information, and `execution_authorized: false`.

Successful evidence is stored under:

```text
.agentic-ml/validations/<digest>/
```

Rejected inputs return `blocked`, diagnostics and no successful configuration identity. Existing evidence is preserved.

### 3. `validate_candidate`

```python
validate_candidate(
    request: CandidateRequest,
) -> CandidateResult
```

Checks one concrete parameter selection against a previously validated configuration.

**Request**

| Field | Meaning |
|---|---|
| `project_root: Path` | Experiment repository root |
| `validation_id: str` | Saved configuration validation identity |
| `algorithm: str` | Selected algorithm |
| `parameters: dict[str, JSONValue]` | Proposed parameter values |

Before checking parameters, it verifies that the referenced validation evidence remains intact and current.

**Materialization rules**

| Parameter category | Candidate behavior |
|---|---|
| Fixed | Inherited; an explicit value must match |
| Omitted registry default | Inherited; an explicit value must match |
| Tunable | Candidate must explicitly supply an allowed value |
| Unknown | Rejected |

For example, suppose the configuration fixes `strategy="quantile"`, permits `quantile` between `0.1` and `0.9`, and leaves `constant` at its null default. A candidate supplying `quantile=0.5` returns:

```python
{
    "strategy": "quantile",
    "constant": None,
    "quantile": 0.5,
}
```

It also returns origins identifying those values as `fixed`, `default` and `candidate`.

**Checks and result**

The function rejects missing tunables, unknown parameters, changed fixed/default values, type mismatches, boundary violations and incompatible combinations.

Successful results contain the bound validation ID, algorithm, complete effective parameters and origins. Failed results contain diagnostics and no accepted parameter mapping.

Typing is deliberately strict: `True`, `1`, `1.0` and `"1"` are distinct for categorical, fixed and default comparisons. No implicit string parsing or integer-to-float conversion occurs.

This operation is read-only. It neither samples missing values nor publishes a run or candidate bundle.

### 4. `inspect_validation`

```python
inspect_validation(
    *,
    project_root: Path,
    validation_id: str,
) -> ValidationInspection
```

Reads saved validation evidence and independently checks whether it is still usable.

It checks schemas, bundle contents, checksums and identities, then recomputes the configuration and compares current inputs, registry, harness/library observations and applicable approvals.

**Result**

It returns configuration-result fields plus:

| Field | Meaning |
|---|---|
| `integrity` | Whether preserved evidence is internally valid |
| `current` | Whether it still matches current inputs and environment |

Typical outcomes:

| Situation | Integrity | Current | Status |
|---|---:|---:|---|
| Evidence intact and unchanged | `true` | `true` | `valid` |
| Evidence intact, inputs changed | `true` | `false` | `blocked` |
| Evidence missing or corrupt | `false` | `false` | `blocked` |

Inspection never silently updates saved defaults. Changed inputs require an explicit new configuration validation.

### Shared error behavior

Rejected inputs return diagnostics with a stable code, field, source path, available line/column location and corrective message. Operational failures, such as unavailable storage, raise `ValidationError(code, message)`.

The corresponding CLI commands return JSON and use exit codes `0` for success, `2` for blocked input and `1` for operational failure.

## 2026-11-04T02:57:28.602Z — Assistant (final_answer)

[models.py](/workspaces/agentic-ml/src/agentic_ml/validation/models.py) defines the **request and result objects** used by the validation APIs. It contains no validation rules, file access or training logic.

| Type | Purpose |
|---|---|
| `RegistryDocument` | Type alias for a JSON-compatible registry mapping |
| `ValidationStatus` | Restricts status values to `valid` or `blocked` |
| `RegistryResult` | Returns checked registry metadata, its identity and diagnostics |
| `ConfigurationRequest` | Selects a project root, preserved plan ID and optional registry file |
| `ConfigurationResult` | Returns the validated configuration, saved validation ID and diagnostics |
| `CandidateRequest` | Supplies a validation ID, algorithm and proposed parameters |
| `CandidateResult` | Returns complete effective parameters, their origins and diagnostics |
| `ValidationInspection` | Extends the configuration result with separate `integrity` and `current` flags |
| `ValidationError` | Reports an operational failure using a stable code and message |

The request/result classes are **frozen dataclasses**, so callers cannot reassign their fields. Nested dictionaries remain mutable; the validation implementation copies data to prevent those dictionaries from altering preserved evidence.

This file gives the CLI, API implementations and callers a shared vocabulary for exchanging inputs and outcomes.
