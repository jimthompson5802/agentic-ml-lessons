The plan proposes a new `agentic_ml.extraction` module with three public APIs:

| API | Purpose |
|---|---|
| `inspect_source(SourceRequest) -> SourceInspection` | Inspect a local CSV/Parquet file and report columns, types, row count, file size, content hash and reader settings. |
| `extract_data(ExtractionRequest) -> ExtractionResult` | Apply configured column selection, filters and joins—or invoke a project-owned extraction function—and save the resulting dataset with provenance. |
| `ExtractionError` | Report actionable input, configuration, callback and output failures while preserving the underlying cause. |

Supporting request/result types will carry explicit project roots, source paths, operation settings, output locations and metadata.

`extract_data` will record source/output checksums, effective settings and execution times. It will return success only after output and metadata are complete.

These names and exact signatures are **proposed**; Implementation Phase 1 settles them before code. No new CLI command is currently planned.

| Installed Python API with explicit project root | Matches separate-project usage and root-relative path resolution. |

These responsibilities follow [Data and Features](/workspaces/agentic-ml/docs/specs/design/data-and-features.md) and [Interfaces and Configuration](/workspaces/agentic-ml/docs/specs/design/interfaces-and-configuration.md).

Two choices deserve particular scrutiny:

- **Output replacement:** refusing existing destinations needs a clear rerun policy compatible with future native DVC stages.
- **Callable flexibility:** requiring preloaded dataframes may constrain ordinary project-owned extraction functions unnecessarily.

So the architecture fits, but the API contract needs refinement at the first review gate before implementation.
