# Lessons Learned: #1 Agentic ML Development

Agentic development worked well when supported by clear workflows, reusable skills, and human judgment to set priorities, assess results, and direct the coding assistant through difficult problems. Slow testing consumed significant time and token budget; resolving it required human direction on what to fix and how, highlighting the need to design efficient test strategies and development environments early.

These lessons come from developing the [agentic-ml project](https://github.com/jimthompson5802/agentic-ml), where the agent handled planning, implementation, verification, and GitHub interactions, with human involvement at scope decisions and approval gates. The project's implementation plans, repository skills, and verification records support the observations below.

## What Worked

**The agentic workflow provided a repeatable way to deliver work.** GitHub issues supplied the scope and acceptance criteria; implementation plans broke the work into phases; and the agent used test results to guide implementation. Plans, verification reports, and checkpoints preserved the decisions and evidence needed to resume work. US-03 is a concrete example: its plan records four approved implementation phases, an accepted correction, and delivery through PR #46. The lesson is to give the agent a clear scope, a feedback loop, and a durable record of progress. ([Workflow](https://github.com/jimthompson5802/agentic-ml/blob/main/docs/development-workflow.md), [US-03 plan](https://github.com/jimthompson5802/agentic-ml/blob/main/docs/plans/milestone-1-us-03.md))

**Human involvement was most useful at decision points.** Phase gates gave the developer opportunities to review evidence, resolve scope questions, and authorize the next step while the agent handled implementation within the approved phase. For example, a PR review identified a cost/currency validation defect in US-03. The developer approved the correction, and the agent reproduced the defect, implemented the fix, and verified it before receiving separate publication instructions. This supports keeping human judgment focused on scope, acceptance, and consequential changes. ([Correction record](https://github.com/jimthompson5802/agentic-ml/blob/main/docs/verification/us-03-cost-currency-correction.md))

**Repository skills made the workflow and GitHub interactions repeatable.** Dedicated skills covered issue retrieval, implementation planning, plan execution, scope management, PR creation, and review. They specified details that are easy to miss, such as retrieving all issue comments and checking for an existing PR before publishing. The US-03 records show the resulting chain from issue retrieval through implementation, review, correction, and merge. The lesson is to capture recurring procedures as skills and preserve their outcomes in project records. ([Repository skills](https://github.com/jimthompson5802/agentic-ml/tree/main/.agents/skills), [US-03 delivery record](https://github.com/jimthompson5802/agentic-ml/blob/main/docs/plans/milestone-1-us-03.md))

## What Needed Improvement

**Test feedback became too slow for rapid iteration.** Although initially described as a unit-test problem, much of the documented cost came from integration tests that created environments, installed packages, and initialized dependencies. A macOS hardlink experiment took **23m54s** for the full suite and was rolled back after making performance worse. A later installer-concurrency experiment still took about **20m30s**. Waiting that long for feedback would substantially limit the agent's ability to iterate. ([Hardlink experiment](https://github.com/jimthompson5802/agentic-ml/blob/main/docs/verification/pytest-hardlink-fixtures.md), [Concurrency experiment](https://github.com/jimthompson5802/agentic-ml/blob/main/docs/verification/pytest-installer-concurrency.md))

**Test strategy needed attention earlier.** Parallel execution helped, but individual optimizations did not consistently improve the full suite. Eventually, tests were stratified by milestone and infrastructure responsibility, with different selections for phase gates, story acceptance, and complete verification. The later Linux records show the default selection completing in **3m54s** and the complete suite in **8m03s**, with existing skips disclosed. These are different platforms and test inventories from the earlier macOS runs, so they are not a controlled before-and-after comparison. The lesson is to design test layers early, measure the whole workflow, and preserve full-suite CI coverage while keeping routine development feedback focused. ([Selection evidence](https://github.com/jimthompson5802/agentic-ml/blob/main/docs/verification/milestone-test-selection.md), [Verification policy](https://github.com/jimthompson5802/agentic-ml/blob/main/docs/development/verification.md))

**The local execution environment also mattered.** Using a Linux-based VS Code devcontainer supported faster local test execution in this project. The repository provides a Debian-based Python devcontainer, allowing development on a Mac while test subprocesses run under Linux. This matters for a suite that repeatedly launches Python processes, installs environments, and imports native libraries: those operations incur different operating-system costs on Linux and macOS. The macOS profiling identified substantial first-use native-library import costs and evidence consistent with repeated macOS security assessments. That supports an explanation involving subprocess initialization and dependency loading, although the records do not isolate subprocess handling as the sole cause of the platform difference. The practical lesson is to consider a Linux devcontainer early for this workload, alongside test stratification. ([Devcontainer](https://github.com/jimthompson5802/agentic-ml/blob/main/.devcontainer/devcontainer.json), [Linux base image](https://github.com/jimthompson5802/agentic-ml/blob/main/.devcontainer/Dockerfile), [macOS profiling](https://github.com/jimthompson5802/agentic-ml/blob/main/docs/verification/pytest-import-profile.md))

**Testing the development process added its own overhead.** One unexpected consequence of the TDD approach was that changes to pytest configuration and test selection required additional pytest tests to demonstrate red/green behavior. These tests exercised pytest itself—for example, launching nested pytest sessions to verify selection and worker grouping. They increased the test count and execution time while verifying how the agentic development process works, rather than agentic-ml functionality. The repository now classifies these scheduling and selection checks as infrastructure. Their long-term value needs further evaluation: which should remain as regression protection, how often they should run, and whether their maintenance and execution costs justify keeping them. ([Scheduling regression evidence](https://github.com/jimthompson5802/agentic-ml/blob/main/docs/verification/parallel-test-execution.md), [Infrastructure classification and red/green evidence](https://github.com/jimthompson5802/agentic-ml/blob/main/docs/verification/milestone-test-selection.md))

**Human judgment was needed to direct the coding assistant on what to fix and how to address the testing issues. The assistant could investigate bottlenecks, propose changes, and verify results, but choosing which optimizations to pursue, when to abandon unsuccessful approaches, and how to balance test coverage against iteration speed required human direction.**

Resolving these test issues took a couple of evenings and consumed most of my weekly token budget. The cost went beyond waiting for tests: repeated investigation, optimization attempts, and verification used time and tokens that could otherwise have gone toward feature development. This reinforced the value of addressing test strategy and the local execution environment early.
